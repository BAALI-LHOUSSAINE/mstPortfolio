// 01 — INTRODUCTION

SSH : protocole critique, cible prioritaire

SSH (Secure Shell) est le protocole d'administration à distance incontournable des systèmes Linux/Unix. Chiffré, authentifié, polyvalent — il permet l'accès shell, le transfert de fichiers (SCP/SFTP) et le tunneling. Mais sa configuration par défaut est loin d'être sécurisée et constitue une cible de choix pour les attaquants : scanners automatiques, bots de brute-force et exploits zero-day ciblent en permanence le port 22.

Objectif du projet

Auditer une configuration SSH par défaut, appliquer des mesures de durcissement (désactivation root, clés RSA/ED25519, port knocking, 2FA), configurer Fail2ban et simuler des attaques brute-force pour tester l'efficacité des contre-mesures.

Environnement de test

Toutes les manipulations sont réalisées dans un environnement virtualisé (VM Linux sous VirtualBox/VMware). Ne jamais tester ces techniques sur des systèmes de production sans autorisation explicite.

Les 6 axes de durcissement

sshd_config

Durcissement de la configuration principale du daemon SSH.

Clés RSA/ED25519

Remplacer les mots de passe par une authentification par clé cryptographique.

Port Knocking

Masquer le port SSH derrière une séquence secrète de paquets.

2FA / TOTP

Ajouter un second facteur d'authentification (Google Authenticator).

Fail2ban

Bannir automatiquement les IP après N tentatives échouées.

Test Brute-force

Simuler des attaques avec Hydra/Medusa pour valider les défenses.

// 02 — AUDIT DE LA CONFIGURATION PAR DÉFAUT

Ce que SSH expose sans durcissement

Sur une installation fraîche Ubuntu/Debian, OpenSSH écoute sur le port 22 avec des paramètres qui favorisent la compatibilité au détriment de la sécurité. Voici les vulnérabilités les plus critiques d'une configuration par défaut.

Paramètre par défaut Valeur Risque
PermitRootLogin yes Connexion root directe possible → compromission totale si le mot de passe est faible
PasswordAuthentication yes Brute-force de mot de passe possible indéfiniment si aucun rate-limiting
Port 22 Scanné en permanence par des bots automatiques (Shodan, Masscan…)
MaxAuthTries 6 6 tentatives par connexion — suffisant pour tester des dictionnaires
X11Forwarding yes Surface d'attaque inutile si pas besoin d'interface graphique distante
Protocol 2 (parfois 1) SSHv1 (obsolète) contient des vulnérabilités cryptographiques critiques
LoginGraceTime 120s 2 minutes pour s'authentifier — facilite les attaques lentes
bash — Vérifier la config actuelle 
# Version OpenSSH installée
ssh -V
# → OpenSSH_8.9p1 Ubuntu-3ubuntu0.6, OpenSSL 3.0.2

# Lire la configuration active (inclure les fichiers supplémentaires)
sudo sshd -T | grep -E "permitrootlogin|passwordauthentication|port|maxauthtries|protocol"

# Vérifier que le service écoute bien
ss -tlnp | grep ssh
# → LISTEN 0  128  0.0.0.0:22  0.0.0.0:*  users:(("sshd",pid=...))

# Scanner les ports ouverts depuis l'extérieur (simulé)
nmap -sV -p 22 127.0.0.1
# → 22/tcp open ssh  OpenSSH 8.9p1 Ubuntu ← exposé !
// 03 — HARDENING : sshd_config

Durcissement de la configuration principale

Le fichier /etc/ssh/sshd_config est le point de contrôle central du daemon SSH. Chaque directive modifiée réduit la surface d'attaque. Voici l'avant/après.

❌ AVANT — Configuration par défaut

# /etc/ssh/sshd_config (défaut)
Port 22
Protocol 2
PermitRootLogin yes
MaxAuthTries 6
PasswordAuthentication yes
PermitEmptyPasswords no
X11Forwarding yes
LoginGraceTime 120
UsePAM yes
AllowTcpForwarding yes
PrintMotd yes

✅ APRÈS — Configuration durcie

# /etc/ssh/sshd_config (durci)
Port 2222
Protocol 2
PermitRootLogin no
MaxAuthTries 3
PasswordAuthentication no
PermitEmptyPasswords no
X11Forwarding no
LoginGraceTime 30
UsePAM yes
AllowTcpForwarding no
PrintMotd no
PubkeyAuthentication yes
AuthorizedKeysFile .ssh/authorized_keys
MaxSessions 3
ClientAliveInterval 300
ClientAliveCountMax 2
Directive Valeur durcie Justification
Port2222Évite les scanners automatiques qui ciblent le port 22
PermitRootLoginnoForcer une élévation de privilèges explicite via sudo
MaxAuthTries3Limiter drastiquement les tentatives par connexion
PasswordAuthenticationnoClés uniquement — rend le brute-force mot de passe inutile
X11ForwardingnoDésactiver si inutilisé (surface d'attaque)
LoginGraceTime3030 secondes max pour s'authentifier
AllowTcpForwardingnoEmpêche l'utilisation de SSH comme tunnel non autorisé
ClientAliveInterval300Couper les sessions inactives après 10 minutes
bash — Appliquer et valider 
# Éditer la configuration
sudo nano /etc/ssh/sshd_config

# Tester la syntaxe AVANT de recharger (évite de se bloquer)
sudo sshd -t
# → Si aucune sortie : configuration valide

# Recharger sans couper les sessions existantes
sudo systemctl reload sshd

# Vérifier que les changements sont actifs
sudo sshd -T | grep -E "port|permitrootlogin|passwordauthentication|maxauthtries"
# port 2222
# permitrootlogin no
# passwordauthentication no
# maxauthtries 3

⚠️ Ne jamais se bloquer !

Toujours garder une session SSH ouverte pendant les modifications. Tester la nouvelle configuration dans un autre terminal avant de fermer la session courante. Sur VPS, avoir accès à la console d'urgence (KVM/IPMI) en cas de blocage.

// 04 — AUTHENTIFICATION PAR CLÉS RSA/ED25519

Remplacer les mots de passe par la cryptographie

L'authentification par clé publique/privée est le mode le plus sécurisé pour SSH. On génère une paire de clés : la clé privée reste sur le client (protégée par une passphrase), la clé publique est déposée sur le serveur dans ~/.ssh/authorized_keys.

RSA vs ED25519 — Quel algorithme choisir ?

CritèreRSA 4096 bitsED25519
Taille de clé4096 bits256 bits
PerformanceLente (grand exposant)Très rapide
Résistance quantiqueNonNon (à terme)
CompatibilitéUniverselleOpenSSH ≥ 6.5 (2014)
Taille signature512 octets64 octets
RecommandationSystèmes anciens✅ Recommandé (2025)
bash — Générer une paire de clés ED25519 
# ── Sur le CLIENT ──────────────────────────────────────────────

# Générer une clé ED25519 avec commentaire et passphrase
ssh-keygen -t ed25519 -C "baali@machine-client" -f ~/.ssh/id_ed25519
# Enter passphrase : [choisir une passphrase forte]
# → Génère ~/.ssh/id_ed25519 (privée) et ~/.ssh/id_ed25519.pub (publique)

# Ou RSA 4096 bits (pour compatibilité)
ssh-keygen -t rsa -b 4096 -C "baali@machine-client" -f ~/.ssh/id_rsa

# Afficher la clé publique à copier sur le serveur
cat ~/.ssh/id_ed25519.pub
# → ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... baali@machine-client

# Copier la clé publique sur le serveur (méthode automatique)
ssh-copy-id -i ~/.ssh/id_ed25519.pub -p 2222 user@serveur

# ── Sur le SERVEUR ─────────────────────────────────────────────

# Vérifier que la clé est bien enregistrée
cat ~/.ssh/authorized_keys
# → ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... baali@machine-client

# Sécuriser les permissions (OBLIGATOIRE)
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

# ── Test de connexion ──────────────────────────────────────────
ssh -i ~/.ssh/id_ed25519 -p 2222 user@serveur
# → Enter passphrase for key '~/.ssh/id_ed25519': [saisir la passphrase]
# → Welcome to Ubuntu 22.04 LTS

# Utiliser ssh-agent pour ne pas resaisir la passphrase
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519

Après avoir testé la connexion par clé

Désactiver PasswordAuthentication no dans sshd_config et recharger le daemon. À partir de là, même avec le bon mot de passe, aucun accès n'est possible sans la clé privée.

// 05 — PORT KNOCKING

Masquer le port SSH derrière une séquence secrète

Le port knocking consiste à garder le port SSH fermé par défaut au niveau du firewall, et à ne l'ouvrir que temporairement après avoir reçu une séquence précise de connexions sur des ports spécifiques — la "séquence de frappe". Un attaquant qui scanne les ports ne verra aucun port ouvert.

1
Le port 2222 (SSH) est fermé par iptables. Nmap ne voit rien.
2
Le client frappe (envoie un paquet TCP) sur le port 7000, puis 8000, puis 9000.
3
knockd détecte la séquence correcte dans les logs du firewall.
4
Knockd exécute iptables -A INPUT -s CLIENT_IP -p tcp --dport 2222 -j ACCEPT.
5
Le client peut maintenant se connecter en SSH. Après déconnexion, le port se referme.
bash — Installer et configurer knockd 
# ── Installation ───────────────────────────────────────────────
sudo apt install knockd -y

# ── Configuration : /etc/knockd.conf ───────────────────────────
sudo nano /etc/knockd.conf
/etc/knockd.conf 
[options]
    UseSyslog
    Interface = eth0    # Adapter selon votre interface réseau

[openSSH]
    sequence    = 7000,8000,9000    # Séquence secrète
    seq_timeout = 10                # 10s pour frapper les 3 ports
    tcpflags    = syn
    command     = /sbin/iptables -A INPUT -s %IP% -p tcp --dport 2222 -j ACCEPT
    cmd_timeout = 30                # Refermer après 30s si pas connecté

[closeSSH]
    sequence    = 9000,8000,7000    # Séquence inverse pour refermer
    seq_timeout = 10
    tcpflags    = syn
    command     = /sbin/iptables -D INPUT -s %IP% -p tcp --dport 2222 -j ACCEPT
bash — Activer le port knocking 
# Activer knockd au démarrage
sudo systemctl enable knockd
sudo systemctl start knockd

# Fermer le port SSH dans iptables (état initial)
sudo iptables -A INPUT -p tcp --dport 2222 -j DROP

# ── Depuis le CLIENT ───────────────────────────────────────────
# Installer le client knock
sudo apt install knockd -y

# Frapper la séquence
knock -v SERVEUR_IP 7000 8000 9000
# → hitting tcp SERVEUR_IP:7000
# → hitting tcp SERVEUR_IP:8000
# → hitting tcp SERVEUR_IP:9000

# Maintenant se connecter
ssh -i ~/.ssh/id_ed25519 -p 2222 user@SERVEUR_IP

# Refermer après usage
knock -v SERVEUR_IP 9000 8000 7000
// 06 — AUTHENTIFICATION À DEUX FACTEURS (2FA)

TOTP avec Google Authenticator

Le 2FA (Two-Factor Authentication) ajoute un second facteur d'authentification en plus de la clé SSH : un code TOTP (Time-based One-Time Password) à 6 chiffres qui change toutes les 30 secondes. Même avec la clé privée volée, un attaquant ne pourra pas se connecter sans le TOTP.

FACTEUR 1 — Clé SSH

Clé privée ED25519 + passphrase. Ce que vous possédez et savez.

FACTEUR 2 — TOTP

Code à 6 chiffres généré par votre smartphone (Google Authenticator, Aegis). Ce que vous possédez.

bash — Installer Google Authenticator PAM 
# ── Sur le SERVEUR ─────────────────────────────────────────────
sudo apt install libpam-google-authenticator -y

# Configurer 2FA pour l'utilisateur courant
google-authenticator
# → Do you want authentication tokens to be time-based? y
# → Affiche un QR code → Scanner avec l'app smartphone
# → Your new secret key is: JBSWY3DPEHPK3PXP
# → Do you want me to update your ~/.google_authenticator file? y
# → Do you want to disallow multiple uses of the same token? y
# → Do you want to enable rate-limiting? y

# ── Configurer PAM pour SSH ──────────────────────────────────────
sudo nano /etc/pam.d/sshd
/etc/pam.d/sshd — Ajouter en tête 
# Ajouter cette ligne EN HAUT du fichier
auth required pam_google_authenticator.so nullok

# nullok : permet la connexion sans 2FA si non configuré pour cet user
# Retirer nullok en production pour forcer le 2FA
/etc/ssh/sshd_config — Activer le challenge-response 
# Activer l'authentification multi-facteur dans sshd_config
ChallengeResponseAuthentication yes
UsePAM yes
AuthenticationMethods publickey,keyboard-interactive

# publickey,keyboard-interactive = clé ED25519 PUIS code TOTP

# Recharger sshd
sudo systemctl reload sshd
user@client:~$ ssh -i ~/.ssh/id_ed25519 -p 2222 user@serveur
Enter passphrase for key '/home/user/.ssh/id_ed25519': ***********
Verification code: 847293
Welcome to Ubuntu 22.04 LTS
Last login: Sat May 20 21:09:39 2025
// 07 — FAIL2BAN : DÉTECTION ET BANNISSEMENT AUTOMATIQUE

Bloquer les brute-forces en temps réel

Fail2ban est un IPS (Intrusion Prevention System) léger qui analyse les logs système, détecte les tentatives d'authentification répétées et bannit automatiquement les IP malveillantes via iptables/nftables.

ATTAQUANT

Brute-force sur SSH

AUTH.LOG

Échecs enregistrés dans les logs

FAIL2BAN

Analyse les logs via filtres regex

SEUIL

N échecs dans T secondes

BAN

IP bannie via iptables DROP

bash — Installation Fail2ban 
sudo apt install fail2ban -y
sudo systemctl enable fail2ban
sudo systemctl start fail2ban
/etc/fail2ban/jail.local — Configuration SSH 
# Toujours créer jail.local (ne jamais modifier jail.conf directement)
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
sudo nano /etc/fail2ban/jail.local
jail.local — Section [sshd] 
[DEFAULT]
# IP jamais bannies (loopback, réseau local)
ignoreip = 127.0.0.1/8 192.168.1.0/24

# Durée du ban : 1 heure
bantime  = 3600

# Fenêtre d'observation : 10 minutes
findtime = 600

# Nombre max de tentatives avant ban
maxretry = 3

# Backend de détection
backend  = systemd

[sshd]
enabled  = true
port     = 2222          # Notre port SSH personnalisé
filter   = sshd
logpath  = /var/log/auth.log
maxretry = 3             # 3 tentatives échouées → ban immédiat
bantime  = 86400         # Ban 24h pour SSH (plus sévère)
findtime = 300           # Fenêtre de 5 minutes
bash — Commandes de gestion Fail2ban 
# Recharger après modification
sudo systemctl reload fail2ban

# Statut général
sudo fail2ban-client status
# → Number of jail: 1
# → Jail list: sshd

# Statut détaillé de la jail SSH
sudo fail2ban-client status sshd
# → Status for the jail: sshd
# |- Filter:  [ Currently failed: 0 ] [ Total failed: 47 ]
# `- Actions: [ Currently banned: 2 ] [ Total banned: 12 ]

# Lister les IP bannies
sudo fail2ban-client get sshd banip

# Débannir manuellement une IP
sudo fail2ban-client set sshd unbanip 192.168.1.50

# Voir les règles iptables actives
sudo iptables -L f2b-sshd -n --line-numbers
// 08 — SIMULATION D'ATTAQUE BRUTE-FORCE

Tester l'efficacité des défenses avec Hydra

Pour valider que nos contre-mesures fonctionnent, nous simulons une attaque brute-force avec Hydra, l'un des outils de test d'authentification les plus utilisés en pentest. Cette simulation doit être effectuée uniquement sur votre propre machine de test.

Usage strictement légal

Utiliser Hydra uniquement sur des systèmes dont vous êtes propriétaire ou pour lesquels vous avez une autorisation écrite. Toute attaque non autorisée est un délit pénal.

bash — Attaque brute-force avec Hydra 
# ── Sur la machine ATTAQUANTE ────────────────────────────────
sudo apt install hydra -y

# Créer un mini-dictionnaire de test
cat > wordlist.txt << 'EOF'
admin
password
123456
root
toor
pass
test
ubuntu
EOF

# Lancer l'attaque brute-force SSH
hydra -l user -P wordlist.txt ssh://192.168.1.100 -s 2222 -t 4 -V
# -l user     : nom d'utilisateur cible
# -P wordlist : dictionnaire de mots de passe
# -s 2222     : port SSH personnalisé
# -t 4        : 4 threads parallèles
# -V          : mode verbose

# Alternativement avec Medusa
medusa -h 192.168.1.100 -u user -P wordlist.txt -M ssh -n 2222 -t 4

// 09 — VÉRIFICATION COMPLÈTE DE LA SÉCURISATION

Audit post-durcissement

Après application de toutes les mesures, on vérifie l'état global du système avec plusieurs outils d'audit.

bash — Audit complet post-hardening 
# ── 1. Scan Nmap externe (point de vue attaquant) ──────────────
nmap -sV -sC -p 2222 192.168.1.100
# Port 22 → filtered (port knocking actif, invisible)
# Port 2222 → filtered (si knocking pas fait)

# ── 2. Vérifier la configuration SSH active ────────────────────
sudo sshd -T | grep -E "port|permitroot|passwordauth|maxauthtries|pubkeyauth"
# port 2222
# permitrootlogin no
# passwordauthentication no
# maxauthtries 3
# pubkeyauthentication yes

# ── 3. Vérifier Fail2ban ───────────────────────────────────────
sudo fail2ban-client status sshd
sudo iptables -L f2b-sshd -n

# ── 4. Tester la connexion légitime ────────────────────────────
knock -v 192.168.1.100 7000 8000 9000
ssh -i ~/.ssh/id_ed25519 -p 2222 user@192.168.1.100
# → Saisir passphrase clé
# → Saisir code TOTP
# → Welcome ✓

# ── 5. Vérifier les logs d'audit ────────────────────────────────
sudo journalctl -u sshd --since "1 hour ago" | grep -i "accepted\|failed\|invalid"

# ── 6. ssh-audit (outil dédié à l'audit SSH) ──────────────────
pip3 install ssh-audit
ssh-audit 192.168.1.100 -p 2222
# → Vérifie les algorithmes, ciphers, MACs recommandés

Récapitulatif des mesures appliquées

 CHECKLIST SÉCURISATION SSH

  • Port modifié : 22 → 2222 — réduit le bruit des scanners automatiques.
  • Root désactivé : PermitRootLogin no — force sudo pour l'élévation.
  • Mots de passe désactivés : PasswordAuthentication no — clés uniquement.
  • Clés ED25519 : algorithme moderne, 256 bits, signatures rapides.
  • MaxAuthTries 3 : seulement 3 tentatives par connexion TCP.
  • Port Knocking : séquence 7000→8000→9000 pour ouvrir le port SSH.
  • 2FA TOTP : second facteur obligatoire via Google Authenticator.
  • Fail2ban : ban automatique 24h après 3 échecs en 5 minutes.
  • Sessions inactives : déconnexion après 10 minutes sans activité.
  • X11/TCP Forwarding : désactivés — surface d'attaque réduite.
// 10 — CONCLUSION

Défense en profondeur : chaque couche compte

Ce projet illustre le principe de défense en profondeur (Defense in Depth) : aucune mesure seule n'est suffisante, mais leur combinaison crée des barrières successives qui rendent l'intrusion exponentiellement plus difficile.

Un attaquant face à notre infrastructure doit contourner : le port knocking (port invisible), les clés cryptographiques (brute-force impossible sur ED25519), le TOTP (même avec la clé volée), et Fail2ban (bannissement immédiat dès 3 tentatives). La combinaison de ces couches rend l'accès non autorisé pratiquement infaisable dans un délai raisonnable.

SIEM

Centraliser les logs SSH dans un SIEM (Wazuh, ELK) pour la détection d'anomalies avancée.

VPN + SSH

Ajouter une couche VPN (WireGuard) : SSH uniquement accessible depuis le VPN.

Honeypot

Déployer un honeypot SSH (Cowrie) pour capturer et analyser les attaques réelles.
