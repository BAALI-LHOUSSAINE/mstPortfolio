Attaque par Saturation

DoS, DDoS, SYN Flood & contre-mesures — Analyse complète

Les attaques par saturation (Denial of Service) figurent parmi les menaces les plus répandues sur Internet. Cet article détaille leurs mécanismes techniques, leurs variantes (volumétriques, protocolaires, applicatives), les outils de détection et les contre-mesures défensives, avec des illustrations concrètes en Python et Scapy.

// 01 — INTRODUCTION

La disponibilité : le pilier oublié de la sécurité

La sécurité informatique repose sur trois piliers fondamentaux — la Confidentialité, l'Intégrité et la Disponibilité — souvent désignés par l'acronyme CIA (Confidentiality, Integrity, Availability). Si les deux premiers piliers concentrent souvent l'attention (chiffrement, contrôle d'accès, signatures numériques), la disponibilité est tout aussi critique mais fréquemment sous-estimée.

Les attaques par saturation (Denial of Service) ciblent précisément ce troisième pilier : leur objectif n'est pas de voler des données, mais de rendre un service inaccessible à ses utilisateurs légitimes, en épuisant ses ressources (bande passante, CPU, mémoire, connexions).

C Confidentialité
I Intégrité
A Disponibilité CIBLÉ
$2.5M Coût moyen d'une attaque DDoS pour une entreprise
3.8 Tbps Record mondial d'attaque DDoS (Cloudflare, 2024)

Cadre légal & éthique

Mener une attaque par saturation — même en "test" — sur un système sans autorisation explicite est un crime informatique punissable par la loi dans tous les pays (article 607-3 du Code pénal marocain, article 323-2 en France, CFAA aux USA). Cet article est exclusivement pédagogique et défensif. Toutes les démonstrations sont réalisées en environnement localhost isolé.

// 02 — DÉFINITIONS

DoS vs DDoS : quelle différence ?

Ces deux termes sont souvent confondus. La distinction est pourtant fondamentale, tant sur le plan technique que défensif.

DoS

Denial of Service

Attaque menée depuis une seule machine vers une cible. Plus facile à bloquer car l'adresse IP source est unique et identifiable.

  • Source unique et traçable
  • Débit limité par la machine attaquante
  • Atténuation simple : blocage IP source
  • Exemples : Ping of Death, Teardrop, Slowloris
évolue vers

DDoS

Distributed Denial of Service

Attaque coordonnée depuis des milliers/millions de machines (botnet). Extrêmement difficile à bloquer car les sources sont distribuées mondialement.

  • Sources multiples et géographiquement distribuées
  • Débit pouvant atteindre plusieurs Tbps
  • Atténuation complexe : scrubbing centers, CDN
  • Exemples : Mirai Botnet, Low Orbit Ion Cannon

Objectifs et motivations des attaquants

Extorsion (RDoS)

L'attaquant exige une rançon sous peine de lancer ou continuer l'attaque. Ransom DoS (RDoS).

Concurrence déloyale

Neutraliser un concurrent lors d'un événement clé (soldes, lancement produit).

Hacktivisme

Protester contre une organisation ou un gouvernement via la perturbation de ses services.

Diversion

Masquer une attaque principale (vol de données) derrière le chaos d'un DDoS pour distraire les équipes SOC.

Cyberguerre

États-nations ciblant des infrastructures critiques adverses (gouvernement, énergie, finance).

Script Kiddies

Attaques opportunistes sans motivation claire, souvent contre des serveurs de jeux en ligne.

// 04 — ATTAQUE PRINCIPALE

SYN Flood : exploiter le three-way handshake

Le SYN Flood est l'une des attaques DoS protocolaires les plus emblématiques et les plus anciennes (documentée dès 1996). Elle exploite une faiblesse fondamentale du protocole TCP dans sa phase d'établissement de connexion.

Rappel : le fonctionnement normal d'une connexion TCP

Dans une connexion normale (vue dans notre article précédent sur les sockets), le serveur alloue une entrée dans sa file des connexions en attente (backlog) dès réception d'un SYN, avant même que la connexion soit confirmée. Cette ressource reste réservée pendant un délai configurable (typiquement 75 secondes sous Linux).

Le mécanisme d'exploitation

SYN Flood — Déroulement
✓ Connexion normale
Client SYN ──────→ Serveur
Serveur alloue une entrée backlog
Client ←────── SYN-ACK Serveur
Client ACK ──────→ Serveur
✓ Connexion établie, ressource libérée
✗ SYN Flood
IP spoofée SYN ──────→ Serveur
Serveur alloue backlog, envoie SYN-ACK
IP spoofée ←────── SYN-ACK Serveur
⚠ L'ACK n'arrive jamais (IP inexistante)
× 100 000 — Backlog saturé → connexions légitimes refusées

Pourquoi l'IP spoofing est crucial dans cette attaque ?

L'attaquant falsifie l'adresse IP source de chaque paquet SYN (IP spoofing). Ainsi :

  • Le serveur envoie ses SYN-ACK vers des adresses inexistantes qui ne répondront jamais
  • L'entrée dans le backlog TCP reste ouverte jusqu'au timeout (SYN_RECEIVED)
  • L'attaquant ne peut pas être tracé facilement
  • Chaque paquet SYN envoyé génère une réservation de ressource côté serveur

La file backlog TCP — ressource critique

Le noyau Linux maintient deux files distinctes : la SYN queue (connexions en état SYN_RECEIVED, taille configurée par net.ipv4.tcp_max_syn_backlog, défaut : 128–1024) et l'accept queue (connexions établies attendant accept()). Un SYN Flood cible la SYN queue. Quand elle est pleine, tout nouveau SYN est ignoré ou rejeté (RST).

Démonstration éducative — Détection d'un SYN Flood avec Scapy

Code de détection uniquement

Le code suivant est un détecteur passif de SYN Flood. Il analyse le trafic entrant et lève une alerte si le nombre de SYN dépasse un seuil. Ce code ne génère aucun paquet d'attaque.

Python — detecteur_syn_flood.py 
from scapy.all import sniff, TCP, IP
from collections import defaultdict
import time

# ─── Configuration du détecteur ──────────────────────────
SEUIL_SYN      = 100   # Nombre de SYN suspects par IP en 10 secondes
FENETRE_TEMPS  = 10    # Fenêtre d'observation en secondes
PORT_SURVEILLE = 80    # Port cible à surveiller (HTTP)

# Dictionnaire : IP source → liste de timestamps des SYN reçus
syn_tracker = defaultdict(list)
alertes_emises = set()   # Évite les alertes répétées

def analyser_paquet(pkt):
    """Analyse chaque paquet capturé et détecte les SYN floods."""
    if not (pkt.haslayer(IP) and pkt.haslayer(TCP)):
        return

    tcp = pkt[TCP]
    ip  = pkt[IP]

    # Filtrer : uniquement les paquets SYN purs (pas SYN-ACK)
    # flags == 0x02 → SYN uniquement (bit S activé, A désactivé)
    if tcp.flags != 0x02:
        return
    if tcp.dport != PORT_SURVEILLE:
        return

    src_ip = ip.src
    now    = time.time()

    # Ajouter le timestamp du SYN reçu
    syn_tracker[src_ip].append(now)

    # Nettoyage : garder uniquement les timestamps dans la fenêtre
    syn_tracker[src_ip] = [
        t for t in syn_tracker[src_ip]
        if now - t <= FENETRE_TEMPS
    ]

    count = len(syn_tracker[src_ip])

    # Affichage temps réel
    print(f"[SYN] {src_ip:20s} → port {tcp.dport} | "
          f"Compteur : {count}/{SEUIL_SYN}")

    # ─── Détection du flood ──────────────────────────────────
    if count >= SEUIL_SYN and src_ip not in alertes_emises:
        alertes_emises.add(src_ip)
        print(f"\n{'='*60}")
        print(f"[!] ALERTE SYN FLOOD DÉTECTÉ !")
        print(f"    IP Source  : {src_ip}")
        print(f"    Port cible : {tcp.dport}")
        print(f"    {count} SYN en {FENETRE_TEMPS}s → seuil dépassé")
        print(f"    Action recommandée : bloquer {src_ip}")
        print(f"{'='*60}\n")
        # En production : appeler iptables/firewall API ici
        # os.system(f"iptables -A INPUT -s {src_ip} -j DROP")

print(f"[*] Détecteur SYN Flood actif sur port {PORT_SURVEILLE}...")
print(f"[*] Seuil : {SEUIL_SYN} SYN/{FENETRE_TEMPS}s\n")

sniff(
    filter=f"tcp and dst port {PORT_SURVEILLE}",
    prn=analyser_paquet,
    store=False
)

// 05 — AUTRES VARIANTES

Autres attaques par saturation détaillées

UDP Flood

Contrairement à TCP, UDP est un protocole sans connexion et sans handshake. Un attaquant envoie des quantités massives de paquets UDP vers des ports aléatoires de la cible. Pour chaque paquet reçu sur un port sans service actif, le serveur doit répondre avec un message ICMP "Port Unreachable", ce qui consomme des ressources CPU et bande passante. À fort débit, la cible est submergée.

Couche cibléeL4 (Transport)
MécanismeSaturation bande passante + CPU
Spoofing requisNon (mais pratiqué)
Débit typiquePlusieurs Gbps
DétectionVolume ICMP anormal
Contre-mesureLimitation ICMP, filtrage UDP

HTTP Flood (Layer 7)

Les attaques applicatives ciblent la couche HTTP en envoyant des requêtes légitimes en apparence mais en nombre massif. Elles sont particulièrement dangereuses car elles ressemblent à du trafic normal et passent souvent les pare-feux réseau classiques. On distingue deux sous-types :

  • GET Flood — Millions de requêtes GET sur des ressources lourdes (images, recherches)
  • POST Flood — Requêtes POST avec des données volumineuses forçant le traitement serveur
Couche cibléeL7 (Application)
MécanismeSaturation CPU/RAM serveur web
Spoofing requisNon (connexion TCP complète)
Débit typiqueFaible (100–10k RPS)
DétectionDifficile (trafic légitime)
Contre-mesureRate limiting, CAPTCHA, WAF

Slowloris — L'attaque "lente"

Inventée par Robert Hansen en 2009, Slowloris est une attaque particulièrement ingénieuse : elle maintient un maximum de connexions HTTP ouvertes en envoyant des requêtes HTTP incomplètes très lentement (un en-tête HTTP partiel toutes les quelques secondes). Le serveur garde ces connexions ouvertes en attendant la fin de la requête, épuisant sa limite de connexions simultanées (MaxConnections) sans générer beaucoup de trafic — pratiquement indétectable par les métriques réseau classiques.

Comportement de Slowloris — Illustration 
# Connexion HTTP normale : rapide et complète
Client → Serveur : "GET / HTTP/1.1\r\nHost: cible.com\r\n\r\n"  # Terminé
Serveur → Client : [réponse complète]

# Slowloris : connexion intentionnellement incomplète
Client → Serveur : "GET / HTTP/1.1\r\nHost: cible.com\r\n"     # Pas de \r\n final !
# Serveur attend... (15 secondes)
Client → Serveur : "X-Header-1: valeur\r\n"                       # En-tête partiel
# Serveur attend encore... (15 secondes)
# → Connexion maintenue ouverte indéfiniment
# × 1000 connexions = serveur saturé sans trafic massif

Attaque par Amplification DNS

Cette technique volumétrique exploite des serveurs DNS publics ouverts (open resolvers) comme amplificateurs. L'attaquant envoie de petites requêtes DNS avec l'IP source spoofée (celle de la victime) vers ces résolveurs. Les serveurs DNS répondent avec des réponses beaucoup plus volumineuses directement vers la victime.

DDoS & Botnets : l'armée de machines zombies

Un botnet est un réseau de machines compromises (appelées bots ou zombies) contrôlées à distance par un attaquant via un serveur C2 (Command & Control). Ces machines sont des ordinateurs personnels, des serveurs, mais aussi et surtout des objets connectés (IoT) — caméras IP, routeurs domestiques, thermostats connectés — souvent peu sécurisés.

Le cas Mirai (2016) — L'attaque qui a bouleversé Internet

En octobre 2016, le botnet Mirai a lancé une attaque DDoS de 1.2 Tbps contre Dyn (un fournisseur DNS majeur), rendant inaccessibles Twitter, Netflix, Reddit, GitHub et des dizaines d'autres services pendant plusieurs heures. Mirai avait compromis plus de 600 000 appareils IoT (principalement des caméras IP et des routeurs) en exploitant leurs identifiants par défaut.

Fonctionnement de Mirai en 3 étapes

  • Scan — Scanner l'ensemble d'Internet (IPv4) sur les ports Telnet (23, 2323) à la recherche d'IoT accessibles
  • Infection — Tenter 61 paires login/mot de passe par défaut (admin/admin, root/12345...)
  • Attaque — Recevoir des ordres du C2 et lancer des floods (SYN, UDP, HTTP GET/POST, GRE Flood)
// 07 — DÉTECTION

Détecter une attaque par saturation

La détection précoce est fondamentale pour limiter l'impact. Plusieurs indicateurs permettent d'identifier une attaque en cours.

Augmentation anormale du trafic

Pic soudain de bande passante entrant sans augmentation du trafic légitime. Un rapport trafic entrant/sortant très asymétrique est suspect (flood volumétrique).

Explosion des half-open connections (SYN Flood)

Commande ss -s ou netstat -an | grep SYN_RECV | wc -l : un nombre élevé de connexions en état SYN_RECV indique un SYN Flood en cours.

CPU/RAM serveur à saturation

Un serveur web dont le CPU atteint 100% sans augmentation réelle de la charge utilisateur légitime peut être victime d'un HTTP Flood ou d'un Slowloris.

Concentration géographique ou par ASN

Une majorité des requêtes provenant d'un même pays, d'un même AS (Autonomous System) ou d'un même fournisseur cloud peut indiquer un botnet ou un attaquant mal dissimulé.

Outil de surveillance réseau en temps réel (Python + Scapy)

Python — moniteur_trafic.py 
from scapy.all import sniff, IP, TCP, UDP, ICMP
from collections import defaultdict, Counter
import time, threading

# ─── Structures de données ────────────────────────────────
stats = {
    'paquets_total' : 0,
    'bytes_total'   : 0,
    'syn_count'     : 0,
    'udp_count'     : 0,
    'icmp_count'    : 0,
}
ip_counter   = Counter()   # Comptage par IP source
port_counter = Counter()   # Comptage par port destination
debut        = time.time()

SEUIL_IP     = 500    # Paquets/10s par IP avant alerte
SEUIL_SYN    = 200    # SYN/10s avant alerte SYN Flood

def analyser(pkt):
    stats['paquets_total'] += 1
    stats['bytes_total']   += len(pkt)

    if not pkt.haslayer(IP): return
    src = pkt[IP].src
    ip_counter[src] += 1

    if pkt.haslayer(TCP):
        port_counter[pkt[TCP].dport] += 1
        if pkt[TCP].flags == 0x02:   # SYN pur
            stats['syn_count'] += 1
    elif pkt.haslayer(UDP):
        stats['udp_count'] += 1
    elif pkt.haslayer(ICMP):
        stats['icmp_count'] += 1

def afficher_stats():
    """Affiche un rapport toutes les 10 secondes."""
    while True:
        time.sleep(10)
        duree = time.time() - debut
        pps   = stats['paquets_total'] / duree
        bps   = stats['bytes_total']   / duree * 8

        print(f"\n{'─'*60}")
        print(f"[RAPPORT] Durée : {duree:.0f}s")
        print(f"  Débit     : {pps:.1f} pkt/s | {bps/1e6:.2f} Mbps")
        print(f"  SYN       : {stats['syn_count']} | UDP : {stats['udp_count']}")
        print(f"  ICMP      : {stats['icmp_count']}")
        print(f"  Top IPs   : {ip_counter.most_common(3)}")
        print(f"  Top ports : {port_counter.most_common(3)}")

        # ─── Alertes ─────────────────────────────────────────
        for ip, count in ip_counter.most_common(5):
            if count > SEUIL_IP:
                print(f"\n  [!] IP SUSPECTE : {ip} ({count} paquets)")
        if stats['syn_count'] > SEUIL_SYN:
            print(f"\n  [!] SYN FLOOD PROBABLE : {stats['syn_count']} SYN détectés")

        # Réinitialisation des compteurs par fenêtre
        ip_counter.clear()
        port_counter.clear()
        stats.update({k: 0 for k in stats})

threading.Thread(target=afficher_stats, daemon=True).start()
print("[*] Moniteur réseau actif — rapport toutes les 10s\n")
sniff(prn=analyser, store=False)

// 08 — DÉFENSE

Contre-mesures et stratégies de défense

La défense contre les attaques DoS/DDoS est un domaine à part entière. Elle s'articule en plusieurs niveaux complémentaires : configuration système, architecture réseau et services spécialisés.

SYN Cookies — La solution native Linux

Les SYN Cookies (RFC 4987) sont la contre-mesure intégrée dans le noyau Linux contre le SYN Flood. L'idée est brillante : au lieu d'allouer une entrée backlog pour chaque SYN reçu, le serveur encode toutes les informations nécessaires dans le numéro de séquence TCP du SYN-ACK. Ainsi, aucune ressource n'est réservée tant que l'ACK final n'arrive pas. Si l'ACK arrive, le serveur reconstitue l'état de connexion à partir du cookie.

Linux — Activation des SYN Cookies 
# Activer immédiatement (temporaire)
sudo sysctl -w net.ipv4.tcp_syncookies=1

# Rendre permanent (après reboot)
echo "net.ipv4.tcp_syncookies = 1" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p

# Autres paramètres de durcissement TCP
sudo sysctl -w net.ipv4.tcp_max_syn_backlog=4096   # Augmenter la file
sudo sysctl -w net.ipv4.tcp_synack_retries=2        # Réduire les retransmissions
sudo sysctl -w net.ipv4.tcp_syn_retries=3           # Réduire le timeout

Pare-feu — Règles iptables anti-DoS

Linux — iptables : règles anti-flood 
# ── Limiter les nouvelles connexions TCP (anti SYN Flood) ──
iptables -A INPUT -p tcp --syn -m limit --limit 25/s --limit-burst 50 -j ACCEPT
iptables -A INPUT -p tcp --syn -j DROP

# ── Limiter les paquets ICMP (anti Ping Flood) ──
iptables -A INPUT -p icmp --icmp-type echo-request \
    -m limit --limit 1/s --limit-burst 5 -j ACCEPT
iptables -A INPUT -p icmp -j DROP

# ── Bloquer les paquets invalides ──
iptables -A INPUT -m conntrack --ctstate INVALID -j DROP

# ── Limiter les connexions par IP (anti HTTP Flood) ──
iptables -A INPUT -p tcp --dport 80 -m connlimit \
    --connlimit-above 50 --connlimit-mask 32 -j DROP

# ── Protection contre le port scanning ──
iptables -A INPUT -p tcp --tcp-flags ALL NONE -j DROP    # NULL scan
iptables -A INPUT -p tcp --tcp-flags ALL ALL  -j DROP    # XMAS scan

# ── Sauvegarder les règles ──
iptables-save > /etc/iptables/rules.v4

Configuration Nginx anti-Slowloris & HTTP Flood

nginx.conf — Configuration défensive 
# Zone de limitation du débit (rate limiting)
limit_req_zone $binary_remote_addr zone=anti_flood:10m rate=20r/s;
limit_conn_zone $binary_remote_addr zone=addr:10m;

server {
    listen 80;

    # Timeouts pour contrer Slowloris
    client_body_timeout   12;  # Corps de la requête : max 12s
    client_header_timeout 12;  # En-têtes : max 12s (clé anti-Slowloris)
    keepalive_timeout     15;  # Keep-alive : 15s
    send_timeout          10;  # Envoi réponse : 10s

    # Limiter la taille des requêtes
    client_max_body_size 10m;
    client_body_buffer_size 128k;

    location / {
        # Appliquer le rate limiting
        limit_req zone=anti_flood burst=50 nodelay;
        limit_conn addr 20;  # Max 20 connexions simultanées par IP

        # Page d'erreur personnalisée si limite dépassée
        limit_req_status 429;
        limit_conn_status 429;
    }
}
// 09 — CONCLUSION

Conclusion

Les attaques par saturation illustrent parfaitement comment un attaquant peut provoquer des dommages considérables sans jamais accéder à une seule donnée confidentielle. La disponibilité est une promesse que chaque service doit tenir, et la défendre exige une approche en profondeur.

Points clés à retenir

  • Un DoS vient d'une seule source ; un DDoS coordonne des milliers de machines (botnet)
  • Le SYN Flood exploite la réservation prématurée des ressources TCP via des IPs spoofées
  • Les attaques volumétriques saturent la bande passante ; les attaques applicatives épuisent le CPU/RAM
  • Slowloris est particulièrement furtif : peu de trafic, mais un maximum de connexions maintenues ouvertes
  • Les SYN Cookies (tcp_syncookies=1) sont la première contre-mesure à activer sur Linux
  • Un DDoS massif nécessite des solutions cloud (Cloudflare, Akamai) — pas gérable seul au niveau serveur
  • La détection précoce (monitoring, seuils, alertes) est aussi importante que la mitigation
